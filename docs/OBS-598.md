**This is a deploy-shape change, not a rename.** Vultr is a raw VM provider
(Cloud Compute + Block Storage + Load Balancer), so the PaaS assumptions the
reference bakes in — a consumed TOML config, an edge-set `fly-client-ip`
header, `fly secrets set`, an auto-provisioned `*.fly.dev` hostname, and the
Let's Encrypt cert via `fly certs add` — each need a Vultr equivalent decided
before the docs/config/guards can change together (changing the docs alone
breaks the OBS-676/OBS-701 guards). The target shape is a design decision and
is routed to the CTO (below), not invented here.

## Design question history (OBS-673)

- "why do we need to run a blockchain relayer ourselves? can't we rely on
  another service so we don't need to worry about security?" was routed to the
  **System Architect** (OBS-673, child of OBS-468, due 2026-11-05).
- Answer (OBS-673, 2026-11-01T16:08:55Z): our smart contract accepts writes from
  exactly one key, so someone on our side must hold it. Moving the server to
  another provider does not move the key or reduce our exposure; handing the key
  to an outside service makes security worse and changes **what** is deployed
  rather than **where**. Recommendation: run our own relayer on a VM inside the
  approved $9.44/month plan / $25.00/month ceiling. Host choice (Fly.io vs
  Vultr vs Netlify) leaves the December audit scope — and its fixed dates —
  unchanged; an outside submitting service would not. The Vultr direction is
  consistent with this answer (same single-key exposure; only the host moves).
